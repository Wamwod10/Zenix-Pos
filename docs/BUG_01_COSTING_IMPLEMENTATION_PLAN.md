# BUG-01 transfer and return costing: implementation plan (approval required)

Status: proposal only; no accounting policy is approved and no backend change or production data correction is authorized. Applies prospectively after business and accounting sign-off. Existing API behavior and tenant isolation must remain compatible; migration must be additive and reviewed separately.

## Proposed policy and examples

At dispatch, lock each tenant/store/product inventory balance and persist its avg_cost as an immutable nullable transfer-line cost snapshot; NULL means unknown, 0 means an explicit free-of-cost item. Record the same snapshot on transfer_out. Destination receipt uses the snapshot, never the current source balance or global product price. Proposed weighted average: new_avg = round((old_quantity * old_avg + received_quantity * snapshot_cost) / (old_quantity + received_quantity), 2). Example: source 10 at 20, destination 10 at 5, receive 5: (10*5 + 5*20)/15 = 10. Empty destination receiving 2 at 1000 produces 2 at 1000. Real zero cost remains zero. PostgreSQL existing balance and movement costs are NUMERIC(18,2): arithmetic should use NUMERIC, with explicit agreed rounding and overflow handling rather than JS floating-point arithmetic. Negative opening quantity, zero denominator and precision-induced valuation residual need explicit policy decisions; do not infer them.

For a return, proposed restoration uses original immutable sale-line unit_cost, and destination weighted average uses returned quantity with that cost; refund profit reverses the same sale COGS snapshot. Example: remaining 10 at 5, return 5 with original cost 20 => (10*5+5*20)/15=10. If existing sale cost is unavailable, reject or classify for manual review according to the approved policy; legitimate zero must not be treated as missing. Approve whether valuation variance needs a separate adjustment ledger and how historical returns are treated.

## Implementation steps (not performed)

1. In backend migrations add nullable cost snapshot/provenance to transfer lines; no rewrite of old rows. Document mixed-version deployments, handling of in-flight legacy transfers, schema verification, rollback and required migration ordering. Backfill is not part of this plan.
2. In src/routes/inventory.js dispatchTransfer, lock source balances in deterministic product order, persist snapshots once inside the existing transaction, attach out movement cost and retain existing tracking. Reject or replay duplicates without changing the snapshot. Tenant/store predicates must guard every read and write. Decide transit valuation and transfer-price versus source-cost accounting before coding.
3. In transfer receipt, lock transfer and destination balances in a consistent order; only once per accepted receipt update quantity and weighted cost together using the dispatch snapshot, and record incoming cost. Existing receipt finalizes with a difference rather than multi-stage receipts: confirm whether the term partial receipt means final discrepancy or additional receipt support. Approve shortage/overage valuation and allow/deny rules before implementation. Handle cancellation and compensation from the immutable snapshot; prohibit double restoration.
4. In src/routes/sales.js, preserve original sale snapshot through refund records and movement cost, apply the approved return valuation under balance lock, and ensure original sale quantity cannot be returned twice. Reconcile refund revenue and reversed COGS with finance reports and dashboard. Do not overwrite existing sales or infer missing history.
5. Add disposable PostgreSQL and HTTP tests with two tenants and branches: receipt/transfer/receipt; sale then refund; different costs; zero cost; changed source cost during transit; final short/over receipt; cancellation before and after dispatch; duplicate receive and concurrent dispatch/receipt; failure injection and rollback; deterministic locking; wrong tenant/store; precision and zero/negative stock; mixed old/new schema and legacy in-flight transfers. Assert movements, stock quantities, stored costs, valuation, COGS, profit and reports against independent NUMERIC SQL.
6. Add Playwright isolated-tenant tests for sale/refund and valuation, run backend and frontend suites, migration status/verify/integrity against disposable DB, and record before/after numeric reconciliation. Do not deploy until all checks and policy approval are complete.

## Historical impact

Existing zero values are ambiguous between valid free goods and missing costs. A read-only tenant-scoped timeline should join receipts, transfer lines, movements, sales and returns, preserve uncertainty and produce an accountant-reviewed impact report. Never use current prices as historical proof. Correction, adjustment entries, migration, production writes and deployments require separate authorization.
